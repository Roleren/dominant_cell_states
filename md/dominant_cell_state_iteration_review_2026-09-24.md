# Iteration review: from atlas to nature-paper factory

Updated: 2026-09-24

## Purpose

This note is written from a different angle than `dominant_cell_state_scientific_note.md`. That note tracks scientific and algorithmic progress on the atlas itself. This one asks the operational question the project is actually funded to answer: **can this compendium reliably produce Nature-worthy hypotheses, cheaply validated in the lab before committing real resources, at a repeatable rate?** That is the only end goal that matters. Everything below is organized around it.

There are currently two active story tracks, at very different maturity levels:

1. **EIF4G2 / tRNA-Glu uORF branch** — a public-data reanalysis finding, artifact-tested to an unusual degree, with a written lab go/no-go plan and a defined cheapest first decisive experiment. This is the template for what "ready to hand to the lab" looks like.
2. **Post-viral fatigue / Long COVID ribosome-decision reprogramming** — a compendium-scale hypothesis with real, quantitative, model-agreement-supported candidates (DDIT3, PPP1R15A, ATF4, IFIH1) and a ranked therapeutic-perturbation hypothesis, but with **no equivalent go/no-go plan and no lab step defined yet**. This is the single biggest gap between the two stories.

The rest of this note works through: what is good and should keep happening as-is, what works but is not optimal, what is genuinely missing, and a prioritized action list for both stories.

## What we have that is good

**The atlas methodology is mature and appropriately paranoid.** `run_dominant_cell_state_pipeline.R` is not a single "compute a score, rank genes" script; it is a 55-step DAG (`--scope all`) that goes from clean-CDS measurement through branch-allocation models, three independent robustness layers (leave-one-study-out, grouped/transportability omission, context-interaction partial pooling), an evidence-gap acquisition queue, active-review batches with a labeling loop, and a claims-ledger discipline that is explicit about what each number does and does not prove. The `eif4g2_claims_evidence_and_gaps.md` "language blacklist" (banning phrases like "causal" or "replicated six times" until specific gates pass) is an unusually rigorous piece of self-discipline for a discovery pipeline and should be treated as a template to copy for the fatigue story, not a one-off EIF4G2 artifact.

**EIF4G2 is about as strong as a pure reanalysis candidate can get before lab work.** It survived: matched tRNA-Arg specificity (Glu-minus-Arg delta -0.147), full raw 16-library reconstruction with per-run/per-length P-site calibration (Gate 6, passed 2026-08-19), coordinate-shift and worst-case position-deletion robustness, a matched total-RNA/isoform audit ruling out the simple confound, and two independent orthogonal recurrences (UV stress, ABCE1 loss). It also connects to an independently published (Kowar et al. 2025) HLA-presented peptide from the exact same uORF — meaning the "why would anyone care" risk is already substantially de-risked before a single lab reagent is ordered. The go/no-go plan correctly identifies the single cheapest decisive experiment (MDA-MB-231 vector/tRNA-Glu/tRNA-Arg × WT/uORF1-start-mutant reporter) and correctly refuses to let a positive UV result substitute for it.

**The environment now actually runs on the full server, not just the local subset.** This was genuinely unverified before this session: the repo had been developed and validated against a subset of `.fst` files on a local machine, and this was the first attempt to run it against the complete backing dataset here. Getting there required finding and fixing several real, previously-invisible bugs (see "What's not optimal" and the appendix), and then actually executing pipeline steps against real data rather than only reading code. `dominant_rdg_sdrive_readiness_audit.R` now reports the all-merged experiment, reference FASTA/index/txdb, count tables, bigwigs, and the all-samples FST index as fully resolved on this server, and `dominant_cell_state_required_fst_pages.R` (a real production step, not a smoke test) completed end-to-end against the full 3,857-run `all_samples-Homo_sapiens` compendium.

**The EIF4G2 raw-data reprocessing was successfully reproduced here using data massiveNGSpipe already had**, rather than re-downloading and re-trimming from scratch. massiveNGSpipe had already fetched and adapter-trimmed all 16 Goodarzi tRNA runs and all 4 GSE141459 UV runs on this server; a new script (`scripts/dominant_rdg_reuse_massivengspipe_length_resolved.R`) filters those collapsed reads to the same 15-40nt window skewer would have produced and aligns directly, and the downstream analysis scripts reproduce the manuscript's qualitative result (uORF1 CPM up / clean-CDS CPM down under tRNA-Glu, `evidence_gate=TRUE`; UV clean-CDS deltas of -0.32/-0.32/-0.21 versus the documented -0.343/-0.341/-0.274). This is a real, verified alternative to the original download+skewer scripts for this server, not just a plan.

## What works but is not optimal

**`clean_cds` could not run at all on a fresh environment: `get_lib_sizes_file()` does not exist anywhere.** It is called (unqualified) in both `dominant_cell_states_fst_clean_cds.R` and `dominant_uorf_regulation_inference.R`, but it is not an ORFik function in any installed version and was never defined in this repo -- it silently worked for the developer only because their local R session must have had it defined from some other loaded source at the time. The real per-sample library-size cache it was clearly meant to read is `QCfolder(df)/totalCounts_mrna.rds` (confirmed on this server: a named numeric vector of length 3,857, exactly matching `nrow(all_samples-Homo_sapiens)`, with sample names as `runIDs(df)` expects). Fixed by defining `get_lib_sizes_file <- function(df) file.path(QCfolder(df), "totalCounts_mrna.rds")` in both files. This one blocked `clean_cds` outright, not just a diagnostic step -- it is the reason a full fresh-checkout run could not get past step 3 before this session.

**The pipeline's own step-level cache silently never worked for `manual_translons`, guaranteeing it reruns in full on every single invocation.** `pipeline_step_outputs()` declared its three output files under `results_dir` (`p("manual_translons", ...)`, same pattern as every other step), but `dominant_manual_translons.R` actually writes them under `<analysis_dir>/manual_translons/` directly -- deliberately outside `results/`, since `manual_translons/translons_to_be_added_to_manual.txt` (the curated input queue) is git-tracked there and the generated manifest/ranges files sit alongside it. Because the cache checked a path that could never exist, this step showed `cache miss: missing output(s)` and fully reran (a genuinely expensive, ~15-20 minute, whole-genome coverage-scoring operation on the all-merged compendium) on every pipeline invocation regardless of `--scope`, `--force`, or prior success. Fixed by pointing `pipeline_step_outputs()`'s `manual_translons` entry at the real `analysis_dir`-relative paths. This was very likely eating real wall-clock time on every iteration the developer ran locally too, not just here.

**A genuine circular bootstrap dependency exists on a fresh checkout.** `manual_translons` is pipeline step 1, but when `manual_translons/translons_to_be_added_to_manual.txt` has pending gene-symbol-based additions (it currently has 26), resolving them to transcript IDs requires `human_dominant_cell_states_clean_cds_gene_diagnostics.csv` — which is produced by `clean_cds`, step 3. On a truly fresh environment with no prior `results/` state, this makes `manual_translons` fail outright (`Could not resolve manual addition gene symbols to transcript IDs`), and because most of the 55-step DAG consumes `manual_translons`' output, a `--keep-going` run cascades failures across nearly everything downstream. This session worked around it by temporarily moving the pending-additions file aside, running `core` scope to bootstrap the diagnostics file, then restoring the file and re-forcing `manual_translons`. This is a five-minute manual fix, but it will recur on every fresh clone/environment and should be closed properly — for example, by falling back to a plain GTF/annotation-based symbol-to-transcript lookup when the diagnostics file does not exist yet, rather than requiring it unconditionally.

**`dominant_manual_translons.R`'s coverage scoring is much slower than it needs to be.** `score_with_merged_rfp()` calls `outputLibs(df_activity, type = "pshifted", ...)`, which resolves to the raw per-read `all.ofst` file for the all-merged compendium library and must fully parse and structure it before computing per-ORF statistics for ~130 candidate regions. The same statistics (`coveragePerORFStatistics()`'s mean/median/ORFScore, which internally calls `coveragePerTiling()` and `orfScore()`) only need per-position, score-weighted depth — exactly what is already sitting, precomputed, in `cov_RLE/all.covqs` (a single merged-across-lengths, P-shifted `covRle`; there is also a length-stratified `cov_RLE_List/all.covqs` if per-read-length resolution is ever needed for a different sub-step). `orfScore()`'s own documentation confirms a score-weighted `GRanges` is an accepted `RFP` input (the same convention bigwig/wig/ofst-derived reads already use), so the fix is not "swap in an Rle" but "convert the covRle's non-zero runs into a scored `GRanges` (one per strand, restricted to the target transcripts' chromosomes) and pass that as `RFP` instead of the raw ofst." This was diagnosed and confirmed correct in this session but deliberately not shipped under time pressure, since it touches real P-site scoring that downstream claims depend on — it should be implemented and verified against the current ofst-based numbers for a handful of known transcripts (SNAI2, MMP2, LMNB1) before being trusted for the full manual-translon set.

**Model agreement is estimator stability, not independent validation, and the project's own scientific note already says so.** The hierarchical-joint and posterior-predictive branch layers share the same grouped branch-count foundation, so high agreement between them mostly confirms that shrinkage/aggregation choices preserve direction, not that two independent methods converged. This is a real ceiling on how much the current "consensus" tier can be trusted without browser labels, and it is the reason the note's own roadmap calls for a true joint multilevel model (gene, study, branch, context, motif prior, protocol effects estimated together) rather than more independently-audited-then-combined layers. Worth tracking as the single highest-leverage modeling investment once label collection (below) is further along.

**The EIF4G2 raw-data reprocessing scripts are not portable, and now have two divergent implementations.** `download_goodarzi_trna_rpf_fastq.sh` / `process_goodarzi_trna_length_resolved.sh` / `process_gse141459_length_resolved.sh` hardcode the developer's local machine (`/media/roler/S/...`, `/home/roler/bin/STAR-2.7.4a/...`, a `skewer` binary that is not installed on this server at all). The new reuse-based script built this session is a validated substitute for this server, but the two paths (fresh skewer reprocessing vs. reused massiveNGSpipe data with a length filter) are not numerically identical, only directionally/qualitatively consistent. A decision is needed: adopt the reuse path as the documented server-side method (fast, already working), or fix the original scripts' portability and install `skewer` for exact parity with the frozen Gate 6 numbers. Either way, this should not remain implicit.

**Validation labels are positive-heavy and this limits how much the review loop can improve calibration.** As of the last labeling pass: two positive labels (`DDIT3`, `ATF3`, both viral infection), zero negative, zero weak-positive, zero confounded, zero measurement-problem, zero negative-control labels. Motif-prior calibration and context filters cannot learn what a false positive looks like from positives alone. The atlas browser's `Review Workbench` and `Label Dashboard` already support pulling negative-control and measurement-risk rows specifically; the gap is that this has not been done yet, not that the tooling is missing.

**Four genes queued in the manual-additions file cannot resolve at all, and the failure mode is all-or-nothing.** `manual_translons/translons_to_be_added_to_manual.txt` includes `ZNFX1`, `IFIT2`, `PELO`, and `HK2` (9 of its 26 rows), but none of these four gene symbols exist in `dominant_state_module_definitions.R` -- the actual source of the ~104-gene marker panel that `clean_cds` measures and that `manual_translons`' gene-symbol lookup depends on. This is not a fresh-checkout artifact: it would have failed identically for the original developer, since PELO and HK2 are explicitly called out in the scientific note's 2026-06-16 entry as needing special handling ("all PELO/HK2 manual features were missing from the current ORFik/Transcode union, which confirms why the manual bridge is still needed"), and `LMNB1` -- the one gene in the current hardcoded `fixed_manual_targets` table -- shows the correct pattern: give it an explicit `tx_id`/`tx_start`/`tx_end` directly rather than relying on the free-text queue's gene-symbol lookup. `manual_translons.R` also treats any single unresolvable row as a hard stop for the whole step (`stop("Manual additions could not be resolved...")`), rather than resolving what it can and warning about the rest. For this run, the 9 blocked rows were set aside (original 26-row file preserved and restored afterward) so the other 17 could proceed; ZNFX1/IFIT2/PELO/HK2 need either an explicit `fixed_manual_targets` entry each, or the marker panel itself needs extending to include them, before they can rejoin the queue.

## What is missing

**EIF4G2's entire causal chain (manuscript Figure 4) does not exist yet, and the manuscript itself says no Results text may describe it until it does.** This is the reporter assay with WT / uORF1-start-mutant / GAG→GAA / codon-5-pause / non-Glu-control constructs crossed with vector/tRNA-Glu/tRNA-Arg (and, orthogonally, HeLa untreated/UV); mature-tRNA-versus-fragment measurement; endogenous DAP5 protein; and targeted immunopeptidomics for the exact peptide. The good news is that the smallest piece of this — the MDA-MB-231 reporter screen — is fully specified in `eif4g2_lab_go_no_go_plan.md` with pre-registered go/stop criteria and an explicit spending ladder, and is ready to hand to the lab today. Nothing computational blocks this from starting.

**The fatigue/Long-COVID story has no equivalent lab plan, and this is the largest strategic gap in the whole project right now.** The atlas already produces specific, quantitative, ranked candidates for it: DDIT3 (+87% clean-CDS, current top consensus anchor), PPP1R15A (+128%, replicated/transport-robust), ATF4 (+81%, direction-robust), IFIH1 (+38%, context-dependent), with a therapeutic-perturbation layer that ranks "ISR/eIF2B-ATF4 attenuation" as the #1 hypothesis and gives quantified half-normalization targets. Separately, `md/long_covid_me_cfs_medications_overview.md` establishes that **no existing approved Long COVID/ME-CFS therapy targets the ISR/ATF4/uORF axis** — the closest things in clinical use (JAK inhibitors, metformin/AMPK) are indirect at best. That combination — a compendium-derived, quantitatively ranked, mechanistically specific hypothesis sitting in genuine therapeutic white space — is exactly the situation the EIF4G2 go/no-go framework was designed for, and it has not yet been written for this story. This should be the next document produced, modeled directly on `eif4g2_lab_go_no_go_plan.md`.

**Update: the first full, successful, all-scope pipeline run on this server completed during this session.** The bootstrap circular dependency above was hit and fixed on the very first attempt, and three more real bugs surfaced only by actually running the code end to end rather than reading it: `get_lib_sizes_file()` was undefined anywhere and blocked `clean_cds` outright (fixed by pointing it at `QCfolder(df)/totalCounts_mrna.rds`); the `glmnet` and `randomForest` R packages were not installed at all, breaking every step that depends on them (`uorf_structure` -> `next_model` -> the entire hierarchical/consensus/therapeutic chain); and `ggrepel` was missing too, blocking `model_agreement_transport`. A fourth issue, `motif_prior_calibration` reading `dominant_rdg_atlas_cards.csv` before that file exists (a genuine forward-reference: `rdg_atlas_cards` runs *later* in the same scope), meant that step -- and `rdg_validation_labels` downstream of it, via an undefined `count_cols` when `motif` has zero rows -- could only succeed on a second pass once the first pass had produced `dominant_rdg_atlas_cards.csv`. After installing the three missing packages and doing that second pass, **54 of 55 steps now succeed** (37 fresh + 17 correctly cache-reused); the only remaining failure is the already-documented `manual_translons` 4-gene curation gap above. The run produced real output consistent with the developer's local-subset results: 1,148 atlas rows across 82 genes and 14 design families, with `ISR/eIF2B-ATF4 attenuation` still ranked the top mechanistic-preclinical therapeutic hypothesis (score 0.77) and `JAK/STAT IFN attenuation` second (score 0.72, the only hypothesis here mapped to already-approved drugs: baricitinib, ruxolitinib, tofacitinib). This is strong evidence the atlas is now genuinely reproducible on the full compendium, not just artifacts of the developer's local subset -- though a full numeric reconciliation against every figure quoted in `dominant_cell_state_scientific_note.md` has not been done row-by-row and should not be assumed exact.

## Prioritized next steps

1. **EIF4G2**: hand the MDA-MB-231 reporter screen to the lab now. It is the cheapest, most decisive, fully specified experiment in the project, and nothing computational should delay it further.
2. **Fatigue/Long-COVID**: write a go/no-go plan modeled on the EIF4G2 one, anchored on the single strongest and cheapest-to-falsify candidate (DDIT3 or PPP1R15A viral-infection clean-CDS effect), with a pre-registered effect-size threshold and an explicit statement of what a negative result would mean for the ISR-attenuation therapeutic hypothesis. This is the highest-leverage document that does not yet exist.
3. Close the `manual_translons` / `clean_cds` circular bootstrap dependency so a fresh checkout does not need manual intervention to get past step 1.
4. Implement and numerically verify the `covRle`-based rewrite of `score_with_merged_rfp()` (see above) — likely turns a many-minutes step into a near-instant one on every future cold run.
5. Decide and document the EIF4G2 raw-data reprocessing path for this server (adopt the reuse script vs. fix portability + install `skewer` for exact Gate 6 parity), rather than leaving two silently-diverging implementations.
6. Deliberately collect negative, weak-positive, and confounded validation labels via the Review Workbench, not only top-score positive candidates — this directly unblocks better motif/context calibration.
7. Finish the full-server `--scope all` run started this session, and reconcile its numbers against the ones currently quoted in `dominant_cell_state_scientific_note.md` before treating the two as interchangeable.
8. Once the lab's improved translon predictor and the p-shift denoising model land (both already in development per the scientific note), revisit iORF/off-frame claims in both stories under real statistical support — this is plausibly where the most novel remaining content in the fatigue story specifically is hiding, since it is currently held at "diagnostic, not claimable."
9. Add a **ribosome rescue/RQC (PELO/ABCE1)** dominant-state module — see `dominant_state_gene_set_theory_and_priorities.md` for the full theoretical and compendium-feasibility case. This is the single highest-priority *new* module beyond the two existing stories: it already has one confirmed hit (EIF4G2 x ABCE1), real sample support (~62 runs), and strong mechanistic priors, and asks directly whether other genes besides EIF4G2 show the same uORF-ward redistribution under the same perturbation class.

## Appendix: this session's environment work (for provenance)

Fixed the same class of bug (RiboCrypt's `collection_dir_from_exp()` resolving to `collection_tables` when this project's own convention, confirmed against `dominant_cell_state_pack_fst_pages.R`'s own documented path, is `collection_tables_indexed`) across 7 production scripts. Fixed the `all_samples_fst_index` path to resolve via `ORFik::config()` instead of a hardcoded S-drive-relative path. Replaced 21 scripts' hardcoded local metadata-file path and 9 references to `human_all_merged_l50` (the developer's local library name) with the server's real `all_merged-Homo_sapiens`, both via environment-variable-driven multi-candidate resolution. Built and validated `scripts/dominant_rdg_reuse_massivengspipe_length_resolved.R` as described above.

Running the full pipeline end to end (not just reading the code) surfaced three more real bugs beyond the ones already covered above: `get_lib_sizes_file()` was called in two scripts but defined nowhere and is not an ORFik function in any version -- it was blocking `clean_cds` outright; fixed by pointing it at ORFik's real per-sample cache (`QCfolder(df)/totalCounts_mrna.rds`, verified to be a length-3,857 named vector matching the compendium exactly). `pipeline_step_outputs()` declared `manual_translons`' outputs under `results/`, but the script deliberately writes them under `<analysis_dir>/manual_translons/` instead (that directory's queue file is git-tracked), so this ~15-20 minute whole-genome coverage-scoring step silently never cache-hit and reran on every single invocation regardless of `--force`; fixed the declared path. And the `glmnet` R package was not installed on this server at all, which would have silently failed every glmnet-based step (motif-prior calibration, several hierarchical/context models) for the rest of the "rdg" scope; installed it mid-run. Separately, `results/curated_inputs/postviral_fatigue_dominant_state_genes.csv` did not exist on this server, so the post-viral fatigue dominant-state module had been silently scoring as empty (0 genes) in every run; reconstructed from the gene lists documented in `postviral_fatigue_translation_note.md` and verified to load (26 up-genes, 17 down-genes) -- see `dominant_state_gene_set_theory_and_priorities.md` for the full theory/feasibility analysis this was part of. Also found: 4 of the 26 genes queued in `manual_translons/translons_to_be_added_to_manual.txt` (ZNFX1, IFIT2, PELO, HK2) cannot resolve against the current ~104-gene `clean_cds` marker panel at all (they are not in `dominant_state_module_definitions.R`), and `manual_translons.R` treats any single unresolvable row as a hard stop for the whole step rather than resolving what it can -- worked around by temporarily excluding those 9 rows, running with the other 17, then restoring the original tracked file afterward. Finally: `--rdg-plot-mode all` (the default) generates one PNG per gene-per-dominant-state overlay and is dramatically slower than `--skip-rdg-plots`/`--rdg-plot-mode tables` for a full "all"-scope run; the project's own scientific note already recommends tables mode for most iterations, which this session's timing confirms concretely rather than just by advice.

A second full pass surfaced three more real gaps, all now resolved: `randomForest` and `ggrepel` were also not installed (breaking `uorf_structure` -> `next_model` and `model_agreement_transport` respectively; installed both). And `motif_prior_calibration` reads `dominant_rdg_atlas_cards.csv` via `atlas <- read_dt(atlas_file)`, but `rdg_atlas_cards` (the step that produces that file) runs *later* in the same pipeline scope -- a genuine forward-reference that can never resolve on a true first pass, only on a rerun after `rdg_atlas_cards` has already produced output once. The same failure then cascades into `rdg_validation_labels`: `count_cols` is only defined inside `dominant_rdg_validation_label_bridge.R`'s `if (nrow(motif))` block (around line 381), and is referenced again later, outside that block, for the `review` table (around line 486) -- if `motif` has zero rows (as it does whenever `motif_prior_calibration` failed upstream), that second reference throws "object 'count_cols' not found" instead of a clear message about the missing dependency. Both resolved themselves once `motif_prior_calibration` succeeded on the rerun; the `count_cols` scoping issue remains a latent bug worth fixing properly (move the definition outside both `if` blocks) even though it is not currently blocking anything.

After all of the above, a second full `--scope all --keep-going --skip-rdg-plots` pass reached **54 of 55 steps successful** (37 fresh `ok` + 17 correctly cache-reused `skipped_cache`), with only the already-documented `manual_translons` 4-gene curation gap remaining. The real atlas output this produced -- 1,148 atlas rows, 82 genes, 14 design families, `ISR/eIF2B-ATF4 attenuation` still the top therapeutic hypothesis at 0.77 -- is discussed above.

All of the above remains uncommitted in this checkout as of this writing, per instruction to hold off pushing until the fuller review is further along.
